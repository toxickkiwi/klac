# Парсер вакансий Минска — бриф и вопросы

Статус: черновик, ждёт ответов на вопросы из раздела 2.

## 1. Бриф (рабочая гипотеза)

### Цель
Автоматически собирать вакансии в Минске с нескольких площадок, приводить их к единому формату, убирать дубли и отдавать результат в удобном виде (таблица / бот / API).

### Пользователь и сценарий (предположение)
Один пользователь (соискатель или рекрутер) хочет видеть все свежие вакансии по своим фильтрам в одном месте, а не открывать 5 сайтов.

### Источники-кандидаты
| Источник | Что там | Способ получения | Риски |
|---|---|---|---|
| rabota.by (семейство hh) | Крупнейшая база по РБ | Официальный API hh (`api.hh.ru`, `area=1002` — Минск) | Нужна регистрация приложения, лимиты; доступ к API надо проверить |
| praca.by | Массовые вакансии | HTML-парсинг | Смена вёрстки, антибот |
| jobs.devby.io | IT | HTML-парсинг | Небольшой объём, но качественный |
| belmeta.com | Агрегатор | HTML-парсинг | Дубли с другими площадками |
| kufar.by (Работа) | Рабочие/линейные вакансии | Внутренний JSON API сайта | Неофициальный API, может измениться |
| gsz.gov.by | Госбанк вакансий | HTML/выгрузки | Медленный сайт, старый формат |
| Telegram-каналы | IT и не только | Telethon / Bot API | Неструктурированный текст — нужен разбор |

MVP: rabota.by + один-два HTML-источника, остальное — по итогам.

### Единая модель вакансии
`id`, `source`, `url`, `title`, `company`, `salary_from`, `salary_to`, `currency` (BYN/USD), `gross/net`, `city`, `district/metro`, `employment` (полная/частичная/проект), `schedule` (офис/удалёнка/гибрид), `experience`, `description`, `skills[]`, `published_at`, `parsed_at`, `hash` (для дедупликации).

### Функции MVP
1. Сбор по расписанию (например, раз в 1–3 часа).
2. Нормализация полей и валют (курс НБРБ для пересчёта USD ↔ BYN).
3. Дедупликация между площадками (компания + нормализованное название + близость описания).
4. Фильтры: ключевые слова, зарплата от, опыт, формат работы.
5. Вывод: CSV/Google Sheets **или** Telegram-бот с уведомлениями о новых вакансиях.

### Вне рамок MVP
Веб-интерфейс, аналитика рынка, отклики от имени пользователя, ML-рекомендации.

### Предлагаемый стек
Python 3.12, `httpx` + `selectolax`/BeautifulSoup, Playwright — только где без него никак; SQLite → PostgreSQL при росте; APScheduler или cron; `aiogram` для бота; Docker для деплоя.

### Нефункциональные требования
- Вежливый парсинг: задержки, соблюдение `robots.txt` и условий сайтов, без обхода защит.
- Каждый источник — отдельный модуль-адаптер, падение одного не ломает остальные.
- Логи и алерт, если источник вернул 0 вакансий (признак сломанной вёрстки).
- Не хранить персональные данные контактных лиц сверх необходимого.

### Этапы и оценка
1. Адаптер rabota.by + модель данных + SQLite — 1–2 дня.
2. 1–2 HTML-адаптера + дедупликация — 2–3 дня.
3. Вывод (бот или таблица) + расписание — 1–2 дня.
4. Docker, деплой, мониторинг — 1 день.

### Критерии готовности MVP
- Собираются вакансии минимум с 2 источников, свежесть ≤ 3 часа.
- Доля дублей в выдаче < 5%.
- Пользователь получает новые вакансии по своим фильтрам без ручных действий.

## 2. Вопросы к заказчику

### Цель и пользователи
1. Для кого парсер: для себя как соискателя, для рекрутинга/HR, для аналитики рынка или как продукт для других людей?
2. Какую задачу он решает в первую очередь: «не пропустить новую вакансию», «увидеть всё в одном месте», «собрать статистику»?
3. Сколько будет пользователей — один или много (нужны ли учётки и личные фильтры)?

### Охват
4. Какие сферы интересуют: только IT, конкретная профессия или все вакансии Минска?
5. Только Минск или ещё Минский район / вся Беларусь / удалёнка из-за рубежа?
6. Какие сайты обязательны? Есть ли источники, которых нет в списке выше (Telegram-каналы, LinkedIn, сайты конкретных компаний)?
7. Нужны ли архивные вакансии или только актуальные?

### Данные
8. Какие поля обязательны (зарплата, стек, контакты, формат работы…)?
9. Нужен ли пересчёт зарплат в одну валюту? В какую?
10. Как поступать с вакансиями без зарплаты — показывать, скрывать, помечать?
11. Нужно ли полное описание или достаточно заголовка + ссылки?

### Частота и объём
12. Как часто обновлять: раз в день, раз в час, почти в реальном времени?
13. Сколько вакансий в сутки ожидается (сотни / тысячи / десятки тысяч)?

### Результат
14. В каком виде нужен результат: Telegram-бот, Google Sheets, Excel/CSV, веб-страница, REST API, рассылка на почту?
15. Какие фильтры и сортировки нужны?
16. Нужны уведомления о новых вакансиях? С какой частотой — сразу или дайджестом?
17. Нужна ли аналитика (средние зарплаты, топ навыков, динамика)?

### Инфраструктура и ограничения
18. Где запускать: локально, на своём VPS, в облаке? Есть ли бюджет на сервер/прокси?
19. Есть ли предпочтения по языку и стеку?
20. Кто будет поддерживать парсер, когда сайты поменяют вёрстку?
21. Есть ли доступ / готовность зарегистрировать приложение для API hh/rabota.by?
22. Планируется ли коммерческое использование данных (важно для условий использования площадок)?

### Сроки
23. Какой срок для MVP и есть ли жёсткий дедлайн?
24. Что считается «готово» для первой версии?
